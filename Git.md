# 🐙 Полная хронологическая шпаргалка по Git для Лабораторной №5

Эта шпаргалка содержит все необходимые команды, разложенные строго по порядку их применения в процессе создания лабораторной работы — от настройки гита до экстренных откатов кода.

## 1. Первоначальная настройка (Один раз на компьютере)
* `git config --global user.name "Твой Никнейм"` — Представиться гиту. Будет отображаться в истории коммитов.
* `git config --global user.email "твоя_почта@example.com"` — Привязать почту (желательно ту, на которую зарегистрирован GitHub).

## 2. Инициализация и связь с GitHub (Один раз при создании проекта)
*Выбери ОДИН из двух путей в зависимости от того, как ты создал репозиторий:*

### Вариант А: Если ты создал пустую папку на компьютере и хочешь связать её с новым репозиторием на GitHub
* `git init` — Создать пустой локальный репозиторий в текущей папке.
* `git remote add origin <ссылка_на_github>` — Связать локальную папку с удаленным репозиторием на GitHub.
* `git branch -M main` — Переименовать главную ветку по умолчанию в `main`.

### Вариант Б: Если ты сначала создал репозиторий на GitHub и хочешь скачать его себе
* `git clone <ссылка_на_github>` — Клонировать (скачать) удаленный репозиторий на твой компьютер вместе со всей историей.
* `cd <название_папки_проекта>` — Перейти в терминале внутрь скачанной папки проекта (обязательно перед вводом других команд!).

## 3. Игнорирование мусора (Делать ДО первого коммита кода)
*Создай в корне проекта файл с именем `.gitignore` и впиши туда системные папки IDE, чтобы они не летели на GitHub. После этого зафиксируй его:*
* `git add .gitignore` — Добавить файл настроек скрытия в индекс.
* `git commit -m "chore: добавить .gitignore"` — Закоммитить файл скрытия мусора.

## 4. Ежедневный цикл разработки (Твоя рутина: написал код -> сохранил)
*Повторяй этот цикл каждый раз, когда сделал логически законченную часть (например, написал класс SpaceMarine, сделал валидацию полей или набросал черновой switch-case).*

* `git status` — Осмотреться. Показывает, какие файлы были изменены, добавлены или удалены с момента последнего сохранения.
* `git diff` — Посмотреть детально, какие конкретно строчки кода изменились.
* `git add .` — Собрать все измененные файлы в коробку для сохранения (подготовить к коммиту). Точка означает "всё текущее".
  * *Альтернатива:* `git add src/models/SpaceMarine.java` — Подготовить к сохранению только один конкретный файл.
* `git commit -m "Твой текст"` — Закрыть коробку, подписать её и сохранить в локальную историю.
  * *Пример:* `git commit -m "feat: добавил модель SpaceMarine с валидацией полей"`
  * *Пример:* `git commit -m "feat: реализовал черновой MVP в классе Main через switch-case"`
* `git push origin main` — Отправить все свои локальные сохраненные коммиты на GitHub. Делай это обязательно в конце рабочего дня или сессии кодинга.

## 5. Безопасные эксперименты (Переход от MVP к Паттерну Command)
*Когда твой черновой MVP полностью работает, переходить на сложный паттерн Command прямо в основной ветке опасно. Сделай для этого отдельную ветку-песочницу.*

* `git branch` — Посмотреть список всех веток. Звёздочка показывает, на какой ветке ты находишься сейчас.
* `git checkout -b feature-command` — Создать новую ветку с именем `feature-command` и автоматически переключиться на неё.
* *... Пишешь классы команд, Invoker, Receiver. Делаешь обычные коммиты через `git add .` и `git commit` ...*

### Если паттерн Command успешно написан и всё работает идеально:
* `git checkout main` — Вернуться на главную ветку со стабильным кодом.
* `git merge feature-command` — Влить все изменения из ветки паттерна Command в твою главную ветку.
* `git branch -d feature-command` — Удалить временную ветку за ненадобностью.
* `git push origin main` — Отправить обновленный итоговый код на GitHub.

### Если ты запутался в архитектуре, всё сломал и хочешь начать переделку MVP заново:
* `git checkout main` — Просто вернись на главную ветку. Там твой код лежит в том чистом виде, каким он был до начала экспериментов с паттерном.
* `git branch -D feature-command` — Жестко удалить неудавшуюся ветку со всем сломанным кодом.

## 6. Просмотр истории проекта
* `git log` — Посмотреть полную историю коммитов (кто, когда и что сделал). Выход из режима просмотра — нажать клавишу `q`.
* `git log --oneline` — Показать историю коммитов в компактном виде (одна строчка — один коммит).

## 7. Кнопка «ПАНИКА» (Исправление ошибок и откаты)

### Ситуация: Ты писал код, запутался, программа не компилируется, и ты хочешь стереть всё, что написал после последнего коммита
* `git restore .` — Очистить рабочую директорию. Удаляет ВСЕ незакоммиченные изменения в текущей папке и возвращает файлы к состоянию на момент последнего коммита.

### Ситуация: Ты сделал коммит, но понял, что написал бред или забыл добавить файл (но еще НЕ делал git push)
* `git reset --soft HEAD~1` — Отменить самый последний коммит. Сам код при этом не удаляется, он просто вытаскивается из "коробки" обратно в статус редактируемых файлов.
* `git add забытый_файл.java` — Добавить то, что забыл.
* `git commit --amend -m "Новое правильное описание"` — Перезаписать самый последний коммит, добавив туда изменения аккуратно.

### Ситуация: Произошел полный хаос, ты стёр что-то нужное, локальный проект уничтожен, но на GitHub лежит рабочая вчерашняя версия
* `git reset --hard origin/main` — ЖЕСТКИЙ ОТКАТ. Полностью уничтожает текущий локальный код и принудительно заменяет его чистой версией, которая прямо сейчас залита на GitHub.
